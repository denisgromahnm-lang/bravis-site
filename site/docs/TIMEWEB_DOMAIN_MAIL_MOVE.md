# BRAVIS — перенос bravisrest.ru из REG.RU в Timeweb Cloud и корпоративная почта
Дата плана: 27.10.2026. Статус: **владелец подтвердил прохождение идентификации ЕСИА в REG.RU 27.10.2026**; остальные условия переноса ещё требуют проверки. Ничего в DNS, REG.RU или Timeweb не изменено.

## Решение по инфраструктуре
- Домен: `bravisrest.ru`, текущий регистратор по заявлению владельца — REG.RU.
- Целевое управление: Timeweb Cloud, отдельный проект **BRAVIS**. Не использовать серверы/балансы проекта A4 REST AI для размещения сайта и корпоративной почты без отдельного согласования.
- Сайт сейчас работает как закрытый `noindex`-предпросмотр на GitHub Pages. `site.config.json: domain=""`, `public=false`, `productionReleaseApproved=false`; не включать до владельческого подтверждения, утверждения юрполитики и актуальности меню.
- Оператор: ООО «Инвойс», официальный текущий email — `bravis.msk@mail.ru`; не заменять его на несуществующий адрес без проверенного получения/отправки писем.
- В Timeweb Cloud домен можно технически подключить до смены регистратора, управляя DNS у текущего держателя NS. Это не то же самое, что перенос регистратора.

## Предлагаемая почта (экономичный вариант)
- **info@bravisrest.ru** — основной настоящий ящик Timeweb Cloud, 120 ₽/месяц по опубликованному тарифу.
- **booking@bravisrest.ru** — бесплатный алиас первого ящика; письма попадают в один inbox. При необходимости отдельного доступа для сотрудника выделить позже второй платный ящик.
- **docs@bravisrest.ru** — дополнительный алиас того же ящика при согласовании; отдельно не включать.
- Алиасы доступны в настройках основного ящика (Timeweb поддерживает до 10 бесплатных псевдонимов, по состоянию на октябрь 2026). Нельзя публично обещать, что они уже существуют.
- Основную почту Mail.ru сохранить на переходный период, протестировать приём/отправку, после чего обновить адрес в site.config.json, юридических текстах, карточках справочников и шаблонах.

## Предварительные проверки (до каких-либо изменений в панели)
1. Установить фактические DNS NS/A/AAAA/MX/TXT/CAA и дату регистрации домена; текущий публичный Whois/DNS из среды работы не подтвержден.
2. **Готово со слов владельца:** идентификация администратора REG.RU через ЕСИА успешно пройдена 27.10.2026. Статус трансфера и ограничения WHOIS проверить отдельно.
3. При полноценном переносе регистратора: нет запрета transfer, более 30 дней с последней смены регистратора/администратора, более 7 дней до истечения регистрации. Запросить AuthInfo через REG.RU, **не публиковать этот код в GitHub, чатах или документации**.
4. Сохранить существующую DNS-зону в резервную копию и зафиксировать, что сейчас использует MX. Если у домена уже есть почта у другого провайдера, выполнить импорт писем перед сменой MX.
5. Убедиться, что замена NS не заденет другие сервисы/домены и проект A4 REST AI.

## Этап 1 — подключить домен и почту технически, без трансфера регистратора
1. В `https://timeweb.cloud/my` → «Домены и SSL» → «Добавить домен»: добавить существующий `bravisrest.ru` в отдельный проект BRAVIS. Не покупать второй домен.
2. «Почта» → «Подключить» → создать `info` у `bravisrest.ru`; пароль сгенерировать в панели, не пересылать и не сохранять в GitHub.
3. «Почта» → настройки ящика → «Алиасы» → добавить `booking` (после подтверждения владельца). Один ящик с двумя адресами экономнее двух независимых ящиков.
4. Настроить следующие записи **только у фактического держателя NS**:
   - MX, хост `@`, приоритет `10`, `mx1.timeweb.ru`
   - MX, хост `@`, приоритет `20`, `mx2.timeweb.ru`
   - TXT SPF (если пока только Timeweb отправляет письма): `v=spf1 include:_spf.timeweb.ru ~all`. Если другие отправители есть, объединить механизмы в ОДНУ SPF, а не создавать две.
   - DKIM: только точное значение из Timeweb, генерируется после создания ящика. Не выдумывать селектор/ключ.
   - DMARC: проверить текущий; на период тестирования допустима мягкая политика `v=DMARC1; p=none`, после устойчивых SPF/DKIM и аудита отправителей можно ужесточить.
5. Тесты: из независимого адреса отправить на info@ и booking@, ответить с info@, проверить заголовки SPF/DKIM/DMARC. Дождаться распространения MX (Timeweb указывает 3–24 часа).
6. После доказанного приёма/отправки обновить на сайте официальный контакт, проверить письма по политике обработки данных и поддержать переходный старый адрес.

## Этап 2 — перенос регистратора, после подтверждения доступности
1. В REG.RU получить AuthInfo через защищённый кабинет, код действует 20 дней (Timeweb).
2. В Timeweb Cloud → «Домены и SSL» → «Перенести домен»; вводить AuthInfo исключительно в защищённой форме панели Timeweb.
3. При старых бесплатных NS `ns1.reg.ru`/`ns2.reg.ru` перенос может снять домен с делегирования. До трансфера сначала перенести DNS на Timeweb, удостоверившись, что ВСЕ нужные записи созданы и работают.
4. Дождаться перевода домена (Timeweb заявляет 5–7 дней), проверить Whois/NS, записи и работу почты. После переноса выполнить ЕСИА-идентификацию в Timeweb Cloud по его правилам.

## Этап 3 — публикация сайта отдельно от mail и регистрации
1. Выбрать подходящий отдельный Timeweb-хостинг для статического сайта; не включать VPS без сметы и разрешения владельца, не размещать на рабочих A4 REST AI серверах.
2. Перенести результат `site/dist`, включить HTTPS для apex и www; проверить сайт до смены A/CNAME.
3. Согласовать актуальные цены/меню и окончательную политику обработки данных. Только после явного одобрения менять `public`, `domain`, `productionReleaseApproved`, индексацию.
4. Настроить A/AAAA/CNAME сайта по фактическим адресам выбранного хостинга. Для www возможен CNAME на основной домен, если провайдер поддерживает. Не выдумывать IP.
5. Проверить BRAVIS, меню, QR Loona, Яндекс Еду, SmartReserve, мобильные версии, cookie и аналитику; затем Вебмастер и справочники.
